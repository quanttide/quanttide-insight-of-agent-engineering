# 循环分类：内置类型还是用户定义类别

判断：循环的三分法（创造环、适应环、控制环）现在应该是用户定义的 category，但系统形态要为它预留晋升为内置 type 的通道。判据不在于分类对不对，而在于系统是否已经为这个区分支付了运行时行为。

## 为什么现在是 category

一、分类目前只是断言，还不是机制。每个环有自己的规格与实现，运行时按环执行，没有任何代码路径根据「这是创造环还是控制环」分支。区分不改变系统行为时，它只是描述性标签——硬编码成枚举，等于把尚在演化的本体论浇进基础设施。

二、边界是谱系而非离散。PDCA 的 Act 步骤本身就带适应性，OODA 结构上近似「敌对环境下的 PDCA」。标错 category 只是说法不对；type 层面的错误分类会触发错误的终止条件、错误的度量，错误被放大了。

三、与档案工程的哲学一致：以实际配置为准，从实践采集，不做设计。这个分类刚从实践日志里提取出来，实践还没验证它，先固化就是凭空设计。

## 为什么它命定会晋升为 type

分类承载着真实的语义承诺——三类环的终止条件、收敛判据、度量方式完全不同。一旦引擎开始统一管理环的生命周期（终止预算、超时策略、度量采集），它就必须知道类别才能选择默认语义。那一刻 category 不再够用，因为委托执行需要机器可检验的约束，而不是自然语言。

这正是渐进类型（gradual typing）的路径：Python 的类型注解先是纯标注，工具链成熟后才逐步进入运行时检查。category 之于 type，正如注解之于语言类型。

## 晋升路径

现在：作为循环规格里的一个普通字段（如 `category: control`），纯元数据，系统不校验、不分支。

同时写下晋升条件，满足才升级为引擎内置枚举：

- 每类有各自不同的默认终止语义；
- 错误分类能被测试检出；
- 新环可以不依赖作者自觉而被归对类。

晋升后仍保留字段形式，存量规格不用改——type 化是加严校验，不是换格式。

## 结论

category 是人用这个区分来交谈，type 是系统押上行为来区分。让这个区分先在实践里证明自己有行为后果，再让它进内核。
